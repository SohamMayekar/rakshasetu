# Decisions

*One paragraph per real decision, with the alternative we rejected. Newest last.*


### D2 · Base images from public.ecr.aws
Docker Hub returns 429 to anonymous pulls in the build sandbox (and venue NAT can trigger the same limit). The Dockerfiles use `public.ecr.aws/docker/library/{python,node,caddy}`, which mirror the official images for free with no account. PostGIS comes from `postgis/postgis` (not mirrored there). **Rejected:** Docker Hub defaults (rate-limited) and a paid registry (zero budget).

### D3 · Plain SQL migrations instead of Alembic; explicit SQL instead of an ORM
Migrations are numbered `.sql` files applied in order by `app/migrate.py` (≈40 lines) as `rakshasetu_owner`, tracked in `schema_migrations`; `grants.sql` is re-applied after every run. Queries use SQLAlchemy Core `text()` with explicit SQL, so every `WHERE` (including the `Scope`, rule R8) is visible in one place, and PostGIS calls (`ST_DWithin`, `ST_Distance`) are written as SQL rather than through GeoAlchemy2 types. **Rejected:** Alembic autogenerate and ORM models (more machinery for every member to explain; ORM queries hide where the scope filter sits).

### D4 · Two database roles; the demo reset is the only owner-level action outside migrations
`rakshasetu_app` (api, worker, ticker) owns no table and has INSERT + SELECT only on `events`, so the application cannot edit or delete history (tested: UPDATE/DELETE/TRUNCATE on `events` and CREATE TABLE are refused). `rakshasetu_owner` runs migrations. The demo reset must clear `events` and write a new genesis event, which the app role cannot do; it will run with owner credentials only when `DEMO_MODE=true` and only from the local listener. **Rejected:** granting TRUNCATE on `events` to the app role (it would let the app erase history silently in normal operation).

### D5 · Demo village: Thawe (Gopalganj), not a Muzaffarpur village
The PRD asked for a Muzaffarpur village whose temple and bridge are both in OSM within 500 m. Measured on the 12 Oct 2026 Bihar extract, Muzaffarpur has 26 mapped village points and 31 places of worship, and no village with a temple–bridge pair under 500 m (best: Sirsian, temple 648 m from the village, bridge 1,186 m from the temple). Thawe in Gopalganj has the village point 42 m from Thawe Durga Mata Mandir, a bridge 112 m from the temple, and no other place of worship within 1 km. The BR incident is "Bihar floods" with two districts, Gopalganj (live desk) and Muzaffarpur. **Rejected:** keeping Muzaffarpur with a fabricated or hand-placed landmark (dishonest), or a Muzaffarpur village with a single landmark (the circle would be 300 m Medium at best and the "temple + bridge" line wouldn't match the data). The humans should confirm this before rehearsal 1 (it changes one word in the pitch line).

### D6 · OSM source: openstreetmap.fr extract, because Overpass is unreachable here
Overpass (and its mirrors and Geofabrik) were unreachable from the build sandbox (the egress proxy drops the connection). The OSM editing API is reachable but its usage policy forbids read-only use (VERIFIED, operations.osmfoundation.org/policies/api). The openstreetmap.fr Bihar extract is an extract download service of the kind that policy recommends, so the gazetteer is built from it. `scripts/import_osm.py` keeps an Overpass mode for a laptop with open internet. **Rejected:** the editing API (policy), a hand-made fixture (not needed: real data was available).

### D7 · Seed cases are generated, with their ground truth beside them
`scripts/gen_seed_cases.py` builds 48 BR reports deterministically from structured choices and writes each choice as `truth`. Until the pipeline exists the loader uses `truth` directly (village-only Low circles, "not triaged yet"); once it exists, seeding runs the texts through the real pipeline and a test compares the pipeline's output with `truth`. **Rejected:** hand-written fields per case (drifts from the text, can't be measured).

### D8 · Relay phone = a phone with two or more separate cases
PRD F-D1 says a phone that "has reported 2 or more different households (different names or headcounts)" stops counting as identity. We operationalise "different households" as **cases that stayed separate** (each refused, suggested-but-unmerged, or new): it is checkable in one query and covers the pradhan, the coordinator and the shared phone. **Known cost** (tested): a son who first gives 6 then 7 people from the same phone produces a suggestion, after which his phone no longer auto-merges; a person merges in one click. **Rejected:** counting only explicit name conflicts (misses a volunteer reporting 10 nameless families of different sizes).

### D9 · The importer is one resumable job; the model reads leftover rows one row per call
The import runs as **one durable job per import** on the `import` lane, not 300 `report.process` jobs: it needs the rows in sheet order (so the file clusters with the same scorer), live counts, and one summary. Each row still commits on its own, with its outcome in `import_rows` **in the same transaction**, so the summary is a count of the database and a killed worker resumes where it stopped (finished rows are skipped; reports are idempotent by file hash + row). Its rows are written with `accept(job=False)` because the import job itself is the durable record of the work; a row whose processing raises is handed to a normal `report.process` job, so nothing is lost. Rows the rules can't place or count go to the language model **after** the rules pass, **20 at a time, one batch at a time** (PRD F-D3) — but **each row is its own call**. **Rejected:** one prompt with 20 rows in it: a model quote could then come from a neighbouring row and still pass the quote check, which breaks "every fact has a quote from its own report". **Cost:** more calls (each with the system prompt), so on the free tier a sheet with many unreadable rows takes longer; the rules-first pass is what keeps it fast.

### D10 · Sheet rows auto-merge only when the pins are good enough
Auto-merge needs 0.85 (with a phone match, place or geo, and no conflict). A sheet row whose place is "village only" (a Low circle) gets no geo signal, so phone + village + headcount + time (0.65) is a **strong suggestion**, not a merge. A row with a landmark that resolves to a Medium pin does auto-merge. We keep the bar as it is: a village-level match is exactly where two families share a relay phone. **Consequence for the demo sheet (m31):** the "merged" share of rows depends on how many rows name a mappable landmark, and the generator reports what it produced rather than targeting the PRD's illustrative 109.

### D11 · Plain Tailwind components, not the shadcn/ui generator
The design system is a handful of hand-written components on Tailwind tokens (`components/ui/`). The desk has no modals, toasts or menus by design (PRD §13.5), which is most of what shadcn/ui and Radix bring, so the generator would add dependencies and generated code we'd then have to own. **Rejected:** shadcn/ui (CLAUDE.md §5 lists it; we keep its spirit — small, owned, accessible components — without the generator). Revisit if a real menu or dialog is ever needed.

### D12 · A refusal's names are shown in ink, not red
The PRD asks for refused pairs to show their names "in red", and also says hue means priority and nothing else (§13.5 #2). We keep the stricter rule: the names that kept two cases apart ("Rajesh ≠ Ramesh") are an **ink-inverted chip**, the same "look here" treatment as every other attention mark, so red always means P1. **Rejected:** red text for refusals (a P1-red line on a P3 case reads as an emergency).

### D13 · A sheet's plain new cases wait in the queue as one row per import
PRD F-D3 says "only the 'to check' rows enter the queue", and F-C2 says a case without an owner needs a person. A 300-row sheet makes ~190 new cases, ~60 of them P1: listing each would bury everything else; leaving them out would hide P1s nobody owns. So the sheet's new cases **that only wait for a team** enter "Needs you now" as **one row per import** ("188 new cases from this sheet need a team · 34 P1 · 71 P2 …"), sorted by its highest priority and marked broken if any P1 in it has waited past 5 minutes; it opens the import's list filtered to "waiting for a team". Its **to-check rows** (likely duplicate, no place, old report, "done" but matched an open case) come in one by one. **Rejected:** hiding them (a P1 with no owner and no alert is the failure this product exists to prevent); listing every row (the pill would read "▲ 190 new").

### D14 · In a surge the map is an overview: it clusters when zoomed out and follows every 5 s
PRD F-C5 asks that "the map clusters" and §15 that desk interaction stay under 100 ms with 2,000 open cases. Drawing 2,000+ circle polygons and re-sending them every second kept the browser repainting the map almost continuously (measured: opening a case took 1.7–2.8 s). Above **300 placed cases**, therefore, the map clusters below zoom 11. A lone case stays a circle of its true size (hollow when its place is uncertain), never a pin, and the honest circles return from zoom 11. The map's data follows the cases **every 5 s**, not every frame. The queue, the promise bar and the drawer stay live every frame: they are where work happens. Below 300 cases nothing changes. **Rejected:** clustering always (it would hide the circles in the normal demo, which is the point of innovation 2); dropping the map during a surge (the PS asks for the whole picture); per-second map updates (the measured cost above).

### D15 · A scene's reset point is replayed through the API, not loaded from a snapshot
PRD F-C12 asks for a reset point per demo scene. Each one is the seed plus the earlier scenes **played through the real API as the people who do them on stage** (`app/modules/demo/scenes.py`, inputs in `data/scenarios/BR/demo.yaml`), so a reset point is always what the current code would produce, and the audit trail reads like the real run. Two deviations, each an audit event: Boat 2's deadline is moved to now instead of waiting out the demo clock, and a live assignment made by the replay is put on the real clock so it waits for the presenter. **Cost:** resets after the sheet take ~21 s (the 300-row import is 15–17 s of it); the start is 3.4–3.7 s, inside the 10 s target. **Rejected:** per-scene database snapshots (fast, but they rot silently whenever the code changes and can't be checked by a test); a fake clock (the ticker and every deadline would need a second notion of time).

### D16 · A partner annotation changes nothing by itself; the partner log is written by a middleware
PRD §11.4 lets a partner say something *about* an existing thing. Each kind's effect is fixed in our code (`app/modules/partners/service.py`), never by the sender: a credibility note is a chip on one evidence item, a priority is a suggestion that only an officer's Accept turns into a priority call (their own override, with the partner's reason, so the queue's "because" and the audit log both name a person), and an anchor receipt is only ever compared with our chain. The partner log (P1 #13) is written by an HTTP middleware around every signed partner POST, so a call refused before it reaches an endpoint (stale, forged, unknown partner, rate cap) is logged the same way as one that succeeds; the signature check adds whether the signature held through a per-request context variable. The surge generator's lane is excluded (thousands of rows a minute would bury the real calls). **Rejected:** applying a partner's priority directly (a stranger's system would then reorder the officer's queue); logging inside each endpoint (refusals would be missed); a table per kind (one `partner_annotations` table with a `kind` and a jsonb target is what the PRD's data model lists).

### D17 · English only on every screen, for now; the rules still read Hindi and Hinglish
The team asked (12 Oct 2026) for English only on the app and the dashboard "for now". So every screen's own words are English: the reporter page, the family's status page, the team app and the rescue sheet lose their Hindi lines, and the fixed reply is the English sentence (the team's recorded clip moves to `public/audio/en/`). The **demo data is English too**, because the desk shows people's own words: the seed cases, the 300-row volunteer sheet (headers and cells), the surge generator, the neighbour's forward and the son's line. The son's clip is a new synthetic espeak-ng recording of the English line, with its transcript fixture. Each generator keeps its random stream (every English list has the length of the Hinglish one it replaced), so every household, headcount, phone, time and expected import outcome is unchanged: `ground_truth.csv` is byte-identical. **Kept:** the keyword dictionary, the gazetteer's Devanagari names, the sheet header aliases and the Devanagari font, so a Hindi or Hinglish report is still read, placed and displayed correctly (the Hindi demo line and the Hinglish tests still pass). Two small rule changes came with it: English puts the relation before the landmark ("behind the Durga temple"), and quotes no longer stop mid-word. **Cost:** PRD §8's multilingual pitch is not shown on stage until the screens get their Hindi back. **Rejected:** translating only the interface (the desk would still show Hindi in every report, which is what the team asked to avoid).

### D18 · A calmer, warmer look, inside the rules: cards on a canvas, a sidebar, icons; still no colour except priority
The team asked (12 Oct 2026) for a more beautiful, Notion-like interface and shared a reference dashboard (sidebar, greeting, a row of stat cards, rounded white cards, icon circles, pill buttons, an activity feed). We took its **shape** and kept PRD §13.5's **rules**: a warm light canvas with white 20 px cards; a sidebar with icons (an icon rail on the desk so the map keeps its width, one scrolling row on a phone) holding navigation, who is signed in, Sign out and, in a demo, "every person and phone here is synthetic"; a greeting and today's date on Incidents and the date and time on the desk; the promise bar as three cards, each with its promise's icon; queue rows and the case panel led by a priority well; the timeline as an activity feed (one icon per kind of event, the caller's words in a bubble, evidence as file cards); pill buttons; icons from lucide-react (ISC, free). **Refused from the reference:** the line chart, the KPI deltas with green/red arrows, coloured status dots, a light-blue accent, and an "upgrade" card. Colour still means priority only (a soft well of the priority's own hue is the one tint we added), "needs you" is still ink (a broken promise is an ink ring), and every text, role and section name the e2e and the PS rely on is unchanged. **Also:** the demo page's QR codes are now images built from the server's SVG, not injected markup, so nothing on any screen uses `dangerouslySetInnerHTML` (R14).

### D19 · Webhooks are a cursor over the event log and ordinary jobs; facts go out, people don't
PRD §11.4 asks for four outbound webhooks. We read them off the audit event log, which already holds every change in commit order: the ticker keeps one cursor per partner (`webhook_cursors`) and turns new events into `webhook.deliver` jobs, and the worker signs and posts them with the job queue's retries (R20). So there is no outbox table, no new process and no broker, and a delivery is retried the same way as everything else. What is sent is decided here and not by the partner: `report.created` and `case.updated` carry facts, the circle and status but never a phone, a name or the reporter's words; `evidence.created` is for media only, with a 15-minute signed link (our key, the partner's id and the expiry); `audit.head` goes out every 5 min when it has moved. A seed or a demo reset holds an advisory lock that pauses dispatch, and at its end every stream restarts at the head with the queue cleared, so a partner never receives the seed or a replayed scene as news. **Rejected:** writing an outbox row inside every state change (it would touch every module, and the event log already is that record); pushing from `pg_notify` (a missed notification would be a missed delivery, whereas a cursor can't skip); sending the report text (it can hold names and numbers, and a partner needs the facts, not the words).

### D20 · Simplify by hiding and renaming, never by deleting; measure what competes for attention
The team asked (12 Oct 2026) for a product a judge understands in a few minutes: fewer people to sign in as, fewer things per screen, plain words. Every capability stays (the PS's 9 components must remain within 2 clicks of where the golden path shows them, and every test still runs); what changes is what is on top. "Too much" is measured, not argued: `make count` (`apps/web/e2e/count.mjs`) counts the visible controls and pieces of text in a screen's first view at 1366×768 and phone size, before and after each change (`docs/SIMPLIFY_PLAN.md`). **Rejected:** deleting screens or features (the tests and the PS need them; a judge who asks can still be shown); a separate "demo mode UI" (two UIs to keep honest instead of one).

### D21 · The front door asks who you are; signed in, `/` goes straight to your own screen
A judge who opens the address should know in five seconds what the product is for and where to click. Signed out, `/` shows two choices only: "I need help" (the reporter page, for people in danger and their families) and "Control room dashboard" (sign in). The rescue team's app is a link underneath, not a third card, because a team is set up before the disaster and doesn't arrive by the front door. Signed in, a team goes to its app and a duty officer with one incident goes to that desk; the Incidents screen (the national layer, three incidents and the India map) stays for whoever sees several incidents. **Rejected:** a third card for the team app (three equal choices are slower to read); keeping the Incidents screen as everyone's home (one card and a map of India is a click with nothing to decide for a district officer).

### D22 · Three people on the sign-in screen; the other nine stay seeded, off the picker
The picker listed 12 synthetic people, which made the judge choose before understanding. It now lists three, each with what it is for: **Duty officer** (R. Das, the Bihar desk), **Rescue team** (Fire & Rescue Boat 5, the phone app) and **Demo admin** (the scene resets and QR codes, all three incidents). The list lives in the config (`demo.sign_in_picker`), so the team can change it without code. The other nine users (a call-taker, a senior officer, an officer of another district, two state officers, the state viewer and three other team leads) **stay in `users.yaml` and the database**: one permission test per PRD §4.2 row and one IDOR test per resource sign in as them, and rewriting those tests around three users would weaken exactly the rules they protect (a call-taker can't assign; another district's officer can't see Gopalganj; another team's lead gets a 403). Role labels lose their jargon (EOC Duty Officer → Duty officer; System admin → Demo admin). **Rejected:** deleting the nine (the permission and IDOR tests would lose their subjects); hiding them in the web page only (the API would still hand out all twelve).

### D23 · The API keeps its codes; screens say them in plain words, and the copy check enforces it
Plain English on screen ("Urgent", "not checked yet", "Send SDRF Boat 2 · 2.2 km away", "History", "✓ unchanged since it was saved", "the demo clock runs 60× faster") without breaking what depends on the short codes: the queue's chips and action labels, the priority codes and the event types are a contract that the API tests, the partner card and the webhooks rely on. So the queue API is unchanged and the web app translates through one file, `apps/web/lib/words.ts` (the glossary in code). Backend lines that are only ever displayed (the timeline, the overdue and capacity alerts, the voice receipt) were rewritten in place, and the tests that pinned their old wording now assert the new words for the same rule. `make copy-check` gained a second list, screen jargon (provenance, SEOC, hash chain, sha256, ×60, P1 on its own, pipeline, STT, …), checked against the text screens show, not against identifiers. The PS's section names (Assignment · Facts · Timeline & evidence · Audit) and CLAUDE.md's required copy ("contact overdue", "check-in due", "Help assigned", "tamper-evident") stay. **Rejected:** renaming the API's codes (contract churn for partners and ~40 tests, no gain on screen); a translation layer per component (the glossary would drift).

### D24 · The desk keeps three things on top: the promises as sentences, Needs you now, the map
The desk had 71 things in its first view (three promise cards with a sub-label and a five-part sum each, two buttons above the list, two lines and a long button per row, an alert with eight controls). It now keeps the three things a judge needs: the promises as one sentence each (a broken one turns ink and says what broke: "41 urgent families without a team"), the list (each row: place and people, then priority, case and waiting time, and one button), and the map. The sums that prove each promise (reports = cases + merged + to check + not yet read; kept apart; contact overdue) are one click away under "Show details", still clickable to filter the list. The list still never re-sorts under the cursor and still holds every row (scrolling, about six in view), because the queue's order is the product's one rule and nothing in it may be hidden. **Rejected:** paging the list to five rows (an urgent family on page two is a family the officer can't see); removing the sums (they are the proof the promises hold, and a judge may ask).

### D25 · The case panel leads with a summary and one next step; the PS's sections fold below it
The panel used to open on four expanded sections and four buttons (105 things in view with the desk). It now opens on what a judge or an officer needs first: who and how many, where with the honest circle, the status in one plain line, and one button, chosen by the same rule as the queue's row (an answer owed, a silent team, the place, a possible repeat, a team, the check), so the panel and the list never disagree about the next step. The four sections keep the PS's names and their content, collapsed, one click each, with a short hint ("21 events · 5 evidence items"), and a queue action opens the section it needs. Rarer actions (move the place, change the priority, close or cancel, and the rules' "because") are under More. **Rejected:** tabs (a section hidden behind a tab is easier to miss than a folded one in the same column); dropping the "because" line from the panel (it is under More, and the priority word stays on top).

### D26 · Three places in the sidebar; the surge and partner screens live inside Demo
The sidebar had six items (Incidents, Desk · BR, Surge, Audit, Partner log, Demo controls), most of them screens a district officer never opens on an ordinary shift. It now has three: **Desk** (or **All incidents** for someone who sees several incidents), **History** (the audit trail, in plain words) and **Demo**. The surge screen and the partner log are things we *show*, so they are two cards inside Demo, "Show it under load" and "Show a partner system", and their routes are unchanged. For the duty officer on the projector, Demo is the 5-minute script, one line a scene; the reset buttons and QR codes stay with the Demo admin (the API still refuses them to anyone else). **Rejected:** opening the demo controls to the duty officer (a permission change for convenience); deleting the surge and partner pages (components 3 and 9 are shown there).

### D27 · Phone screens: one thing to do on each, and nothing asked of the family
A person in danger, or their son in another city, should not have to choose a mode, remember a code or answer anything. The reporter page shows the microphone and, right under it, the text box with Send: no "Type instead" switch to discover. The confirmation says "We have your report", the fixed reply, and the case number only "in case a rescuer asks"; the call-back number is optional and folded away. The status page says one sentence about where things stand, in the CLAUDE.md copy ("Help assigned", never "on the way"), with the steps a tap away; the family's question stays optional. The team app gives each case one big next action on the list itself, so a team member with wet hands doesn't have to open the case to say "reached". **Rejected:** removing the case number from the confirmation (a rescuer or a call-taker may ask for it; we just never require it); a stepper as the main status (four rows to read where one sentence will do).

### D28 · The demo page is the script: numbered scenes, Next scene, and the honesty lines in view
A presenter under stage lights should not read paragraphs to find the next button. `/demo` now shows the six scenes as numbered buttons, the current one in big type with one line of what to do, and one big "Next scene", which only moves the presenter's place (kept in this browser): the scenes are played live on the desk and the phones, and "Reset to the start of this scene" is the fallback when something goes wrong, not the way forward. The honesty lines sit in view on the same screen ("Say it on stage"), so they are said every time. Everything else (reset to any scene, AI reading on/off, the rush, the partner moment, the clips) is under More controls. **Rejected:** Next scene resetting the database (it would wipe what the judge just watched, and the sheet scene takes 13 s to replay); a separate presenter-notes file (two scripts drift).

### D30 · The desk counts families, not promises
The team asked (12 Oct 2026) whether "never lost, never doubled, never stale" belongs on the screen at all, and asked for an app about saving lives rather than about its own design. The promises stay true and tested (the metrics, T1–T10, the golden path's "adds up" check, the load screen), but an officer doesn't run a shift on "reports = cases + merged + to check". The desk's top row and All incidents now say three things in families: need help now, a rescue team is on it, rescued or closed. A tile turns ink only when lives are at risk (an urgent family without a team for 5 minutes, a team not heard from), which is exactly what "never stale" was guarding. The front door says "Get every family to safety." **Rejected:** keeping the promise sums behind "Show details" on the desk (nobody opens them mid-shift, and the load screen already shows them for whoever asks); a "people rescued" count (the API counts families; a people total would need new code and could double-count trips).

### D31 · The demo is people using it, not the system explaining itself
The team asked for a demo that is real use rather than a staged show. Everything in it already runs on the real code paths (a judge's phone through the public listener, the real pipeline, the real desk, the team's phone); what made it feel staged was narration: the projector captions explained the rules ("nothing is taken away automatically; an officer decides"), and the demo page read like stage directions. Captions now state one fact each, and `/demo` is a run sheet of six things people do, led by a judge asking for help from their own phone. The recorded clip is the fallback when nobody has a phone or there is no speech key, and it is called a recording. The honesty lines stay, said once. **Rejected:** removing the captions (the projector is far from the judges, and the golden path checks them); hiding that data and clock are demo values (CLAUDE.md §1.6).

### D32 · No screen explains how the system works
A real control-room tool doesn't caption itself. Subtitles, footnotes and hints that described the machinery ("each row commits on its own", "measured inside the server", "only a real tap counts as a check-in", "the case stays with the team until you act") were cut; what is left says what is happening to families and teams. The explanations live where they belong: the docs, the teach-back, and the presenter's mouth. Two things stay because people need them to act safely: the 112/1077 line on the phone pages and the team app's one line about check-ins. **Rejected:** tooltips holding the same explanations (hidden filler is still filler, and it hides from judges on a projector anyway).
