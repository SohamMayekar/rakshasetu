# surge · load the system, and watch what it does about it (PRD F-C5)

- **The generator** (`make surge`, i.e. `python -m app.surge --rate 50 --duration 60` inside the api container): HMAC-signed partner reports as the `surge-generator` partner, through the **public** listener (`caddy:8080`), the way a partner's system would send them. Each report is **synthetic and pre-structured**: its facts arrive in the §8.2 shape, every fact with a quote that appears in the text (checked by a test), so **no language model is called**. Say so on stage. 80 % go to BR (12 real places from the gazetteer, 8 with a landmark), 10 % each to OD and HP (district only). 85 % name the family ("Raju Sah ka parivaar"); 20 % of reports repeat an earlier household, with the same phone and name, as a second source would. All names and phones are made up (`+9199…`).
  - **Deviation:** the PRD puts it at `scripts/surge.py`. It lives at `services/api/app/surge.py` so `make surge` runs it in the api container, with nothing installed on the host.
- **Lanes:** a partner's `lane` in `config/partners.yaml` decides where its reports queue. Only `surge-generator` uses the `surge` lane (behind live voice, WhatsApp/partners and imports). A real partner's simulated reports keep their own lane, so a surge never delays them (tested).
- **Ingest timing:** the API times every `POST /v1/ingest/*` in memory, from the request arriving to the receipt (the database write happens first). Nothing is stored; it covers one API process, the only one.
- **`GET /v1/metrics/surge`** (local listener, `totals.view`): the last 60 s of ingest (rate, p50/p95/p99, errors), the backlog per lane (waiting, oldest), and the last minute's reports read, new cases and merges, from the event log.
- **The surge screen** was removed in m83 with the demo page. During `make surge` the desk's numbers and list show the effect; `GET /v1/metrics/surge` still reports rate, p50/p95/p99 and the backlog per lane.
  - **The integrity check runs on request** ("Check again"), not on a timer: it re-walks the whole hash chain (~0.8 s of the API's CPU at 14,000 events). Polled every 10 s during a surge it pushed ingest p95 from ~70 ms to ~810 ms, because the check and ingest share the API process.
- **The desk in a surge** (2,000+ open cases):
  - Queue reads never overlap. Asks that arrive meanwhile collapse into one more read, 2 s later. The list still never re-sorts under the cursor.
  - The drawer fetches its own case's matches (`/v1/merge-suggestions?case=`), not the whole incident's list.
  - Above 300 placed cases the map clusters below zoom 11 (grey bubbles with a count). A lone case is still a circle of its true size, hollow when its place is uncertain; it is never a bare pin. From zoom 11 the honest circles return. The map's data follows every 5 s, while the queue updates every frame. Below 300 cases nothing changes: circles at every zoom, updated every frame (D14).
  - The queue renders 80 rows and offers "Show more (N below, in the same order)".
- **Resetting mid-surge:** the seed pushes waiting jobs an hour out before its wipe, and retries the wipe if Postgres picks it as a deadlock victim. The worker beats its health file after every job, so a long backlog never reads as a hang.
- **What the numbers don't show:** the generator's 2,400 households share 12 places, so village, pin and headcount line up far more often than in a real flood, and "to check" grows to ~3,500. Repeats of district-only households (OD, HP) are never suggested, even with the same phone, because PRD F-D1's minimum evidence needs a place or a geo match (open question in STATUS).
