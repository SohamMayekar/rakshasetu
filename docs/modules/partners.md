# partners · annotations from another team's system, and the partner log (PRD §11.4, P1 #13)

- **One contract.** A partner sends anything that *is* a report to `POST /v1/ingest/reports` (m17) and anything *about* an existing thing to `POST /v1/partners/annotations`. Both are signed the same way (`X-RakshaSetu-Partner`, `-Timestamp`, `-Signature: v1=HMAC-SHA256(secret, ts + "." + raw body)`, 300 s window, per-partner secret, scopes and rate cap), and both need an `Idempotency-Key` header equal to the body's key: a repeat returns the first answer with `Idempotent-Replay: true` and changes nothing. Adding a partner is a row in `config/partners.yaml`; `enabled: false` is its kill switch.
- **Our rules decide what each kind does** (`app/modules/partners/service.py`), whatever the partner meant:

  | kind | target | effect |
  |---|---|---|
  | `credibility` | `{"evidence_sha256": …}` | A chip on **that evidence item** in the timeline ("Demo partner (simulated by RakshaSetu): no earlier copy found · 0.91 · …"). It never blocks or delays a dispatch and never lowers a priority (tested). |
  | `priority` | `{"case": "BR-199"}`, value `P1`–`P4` | A card in the drawer: "*Team* suggests **P1** · 0.78 · *their reason*", with **Accept** / **Ignore** for an officer with `priority.override`. Accept makes it the officer's own priority call (the m57 override), with the reason "accepted *team*'s suggestion (0.78): …". Either choice is an audit event and is made once (a second answer is a 409). Until then the case is unchanged. |
  | `anchor_receipt` | `{"seq": …, "head_hash": …}` | The partner anchored our audit head in its own ledger. The Audit screen and the partner log show "✓ Head #232 anchored by *team*" while our chain at that seq still has that hash, and ✗ once it doesn't. That closes "our own DB admin could re-hash everything": a re-hash makes local Verify pass but the anchored head stops matching (tested by rewriting a row's hash as the database owner). |
  | `identity` | — | Refused with **422** ("not supported yet", PRD: LATER), never silently ignored. |

  Every accepted annotation is stored in `partner_annotations` (unique per partner + idempotency key), is a `partner.<kind>` audit event, and, when it concerns a case, is itself a hashed `partner_annotation` evidence item on that case. A partner can only touch cases in the incidents its row lists.
- **The partner log** (`/partners`, linked from Audit; `GET /v1/partners/log`, local listener, `audit.read`): every signed partner POST, accepted or refused, newest first, with direction, endpoint, status (a refusal shows why, e.g. **"401 · Stale timestamp: replay rejected"**), whether the signature held (✓, ✗, or "–" when it was never checked, e.g. an unknown partner), latency and the body's sha256. A replayed request shows as **signed correctly but too old**, and its body hash equals the original's. A middleware times each call; the signature check and the endpoint add what they know through a per-request record (`partners/log.py`). The surge generator's synthetic load is **not** logged one by one (its lane is `surge`), so it can't bury the calls a person wants to see.
- **The demo partner is simulated, and says so.** `make partner-demo CASE=BR-199` (or the /demo page's "Partner moment") runs `app/partner_demo.py`: our own script, signed as `demo-partner` ("Demo partner (simulated by RakshaSetu)"), through the **public** listener. It sends a priority suggestion whose "gauge G-03" reason is labelled a simulated sensor, a credibility note on the case's first evidence item ("simulated forensics check"), an anchor receipt for our current head ("simulated ledger entry"), and then its first request again with a 15-minute-old timestamp, which is refused. On stage, say it is simulated; a real team's system would send the same calls.
- **Not built yet:**
  - outbound webhooks (`report.created`, `evidence.created`, `case.updated`, `audit.head`) and the one-page contract card: m59
  - `identity` annotations (PRD: LATER)
  - the `low_credibility` case flag: PRD §14 reserves it for a case whose every report is a forwarded photo with no callback phone, and RakshaSetu has no photo intake
- **Deviation:** the PRD calls it the partner log *drawer*; it is a page (`/partners`) linked from Audit, because the desk drawer already belongs to the selected case.
